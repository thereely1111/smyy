### 3.8 运行期重注册把装配工厂降级——选模型 / 联网开关 / 调试草稿静默失效
- **两条注册路径并存且语义不同**：
  - 启动期 `AguiIntegrationConfiguration.aguiRegistryCustomizer()` → `registry.registerFactory(id, () -> assembleForCurrentRun(config))`，该方法调 `assemblyService.assembleForRun(config)`，并在 `finally` 清 `RunModelSelection`；
  - 运行期 `AguiRegistryManager.register()` → `registry.registerFactory(id, () -> assemblyService.assemble(config))`（**纯装配**，不读任何 run 级选择）。
- **为什么这是 run 级入口**：`assembleForRun`（`AgentAssemblyService:483-508`）是**唯一**消费三个 run 级选择的地方——`RunModelSelection.current()`(:484)、`RunWebSearchSelection.isEnabled()`(:485)、`RunDebugSelection.current()`(:490)；而框架 `AguiAgentRegistry.getAgent()` **每次请求**都会 `factory.get()`（`agentscope-extensions-agui/.../AguiAgentRegistry.java:101-110`）⇒ 工厂注册成哪个方法，直接决定该 run 有没有这三项能力。
- **触发面（全部走 `AguiRegistryManager`）**：创建 `AgentConfigService:245`、更新 `:279`、发布 `:298`、状态切换 `:354`、`reload-files` `:834/:838`、**文件智能体发布 `publishFileAgent:705`**。
- **后果（静默、无异常、无告警）**：① 对话选模型失效——回落平台默认装配实例，用户选的凭证/模型不生效；② 联网搜索开关失效——`RunWebSearchSelection` 不被读，关掉也仍然注册搜索工具；③ **调试草稿失效**——DB 智能体只要在启动后被保存过/改过状态，编辑页「试运行」拿到的就是发布配置而非草稿，即 1d2d833 的在线调试在运行期注册路径上不成立。
- **可观测点**：启动期注册打印 `Registered file-agent factory: …` / `Registered AG-UI factory for agent: …`；运行期降级打印 `AG-UI registered agent: …`（`AguiRegistryManager:42`）⇒ 控制台/日志里出现后者即说明该智能体已被降级。
- **修法**：注册统一到 run 级入口——抽出共享装配入口（`AguiRegistryManager` 不再直接 `assemble`），读后清理与启动路径对齐。
- **诚实边界**：两条注册路径 + 框架每请求调工厂已逐行核对（代码可证）；**运行期未复现**——后端跑在 IDE 控制台、日志不落盘，且差异只在真实 run 的模型/工具集上可见。

### 3.2 假活锁：run 租约把停滞看护的闸门长期关死
- **闸门判据（本轮回源，与旧表述不同）**：`SessionProgressService` 的 `shouldWake = idleLong && !finished && !waitingHuman && !pendingInbox && !activeElsewhere && !wakeCapped && canWakeAgain(existing)`，其中 `activeElsewhere = RunLeaseStore.existsBySessionId(sessionId)`——即 **`run_leases` 表里只要有一条该会话的租约，自检就永不触发**。判据不是「子任务 RUNNING 状态」，也不是子任务记录。
- **租约生命周期**（`RunLeaseReconciler`，每分钟巡检）：
  1. `instance_id ≠ 当前进程` ⇒ 判定旧进程遗留，push 恢复提示并删租约（重启后首轮即恢复）——这解释了「重启一次就自愈」；
  2. 本进程 且 `SessionActivityTracker.isRunning(sessionId)` ⇒ **刷新心跳并 return，永不清理**；
  3. 本进程 且 未在跑 且 心跳 >2 分钟 ⇒ 删租约。
- **因此永久阻塞的充分条件是**：`SessionActivityTracker` 的活跃计数泄漏（`doFinally` 未执行，即既有文档所述「僵尸 run 取消链死锁」）⇒ 租约被规则 2 无限续命 ⇒ 闸门条件 `activeElsewhere` 恒真 ⇒ 看护永不介入。
- **唯一的僵尸出口也有盲区**：`RunSilenceDetector`（WARN 20 分钟 / 判死并自动恢复 60 分钟）的扫描源是 **`SessionEventClock.snapshot()`**，而活跃判据取 **`SessionActivityTracker`**——两份登记表若不一致（有 running 计数、无事件时钟条目），该会话**既不告警也不恢复**。登记点同为 `SessionActivityMiddleware.onAgent` 的 `begin/doFinally`，但计数与时钟是两份独立表，结束路径（引用计数、`forceEnd`、`clear`）并非严格同源。
- 现行阈值（`application.yml`）：`stall-min-minutes=8`、`wake-cooldown-minutes=15`、`max-wake-attempts=3`、`stall-alert-min-minutes=30`、静默探测 20/60 分钟。
- 观测事实：04:03 派发之后连续 10 小时零自检（04:03→14:09），进程级重启后恢复（14:17、14:32 连发）。
- 修法：① 闸门不能只看租约**存在性**，应加「心跳陈旧 > N 分钟 ⇒ 视为僵尸租约」；② `RunSilenceDetector` 扫描源改为三方并集（`activityTracker ∪ eventClock ∪ run_leases`），消除两表不齐的盲区；③ 给 `SessionActivityTracker` 的 `begin/end` 加泄漏打点（登记后超阈值仍在 running ⇒ WARN）。
- **诚实边界**：上面是**代码可证的盲区**，但不等于已证实的成因——当时进程已重启、内存态消失，无法回溯那一 episode 究竟是哪份登记泄漏。改造要按「三条都覆盖」来做，不要押在单一假设上。

### 3.7 重启静默杀死在途子智能体（范围已收窄）
- 已具备的能力（本轮核实 `StartupStaleTaskCleaner`）：启动时把「失去执行者的在途任务」标为 `FAILED`，**两种落盘布局都覆盖**（旧布局 `.../agents/{agent}/tasks/{session}.json` 与 2.0.3 的 `.agentscope/bus/async-tools/{session}/call_*.json`），并对受影响会话 push inbox 提示 + `enqueueWakeup` 唤醒父会话，使其按「任务丢失」收敛。
- 因此真实缺口只剩：① 终态语义是 `FAILED` 而非「已中断/可续跑」，而子任务可能已产出全部产物（实训即此情形：5 件产物齐全，却被标 `FAILED`）；② `result` 为空，不告知产物可能已落盘及其位置；③ 30s 关停窗口与实测最坏单步耗时不匹配，「优雅关停」实际会截断；④ 主编无法区分「子智能体自身失败」与「被重启杀掉」。
- 改法：a) 在途任务改专用终态（如 `INTERRUPTED`）+ 产物路径说明；b) 标记时附带「盘上产物清单」；c) 关停等待窗口与实测最坏单步耗时对齐。

### 3.6 后台子任务终态通知噪声
- 来源唯一：`harness/TaskDeliveryWatchdog.notifyTaskTerminal()`（定义 :334，正文模板 :340，`alert_key=task-terminal:{session}:{taskId}` :353）。三分支结构本轮复核：① 转录已有完成标记 ⇒ 只标已投递、不通知；② inbox 已有待消费 hint ⇒ 只标已投递 + 补醒、不通知；③ 两者皆无 ⇒ push hint + 补醒 + **`notifyTaskTerminal` 发人通知**。即通知**只在兜底分支③**触发。

### 3.10 上下文压缩按条数触发/保留——高频 LLM 摘要与压缩后 token 不降

缺陷机制（两处叠加）：

1. **框架：声明式子智能体不继承压缩配置**。`HarnessAgentBuilderSupport.buildGeneralPurposeFactory` 传播 `compactionConfig` / `disableCompaction` / `toolResultEvictionConfig`，而 `buildDeclaredFactory`（AGENTS.md 声明的 subagents，即章节生成/审核等主力子智能体的构建路径）不传播 ⇒ 回落框架默认（50 条消息触发、保留 20 条）。编排型子智能体一轮产生大量小消息，50 条几分钟即攒满，token 远未饱和也反复发起 LLM 摘要。
2. **平台：压缩阈值/尾巴按消息条数表达**。`AgentAssemblyService` 只设 `triggerMessages` / `keepMessages`；当模型不上报上下文窗口时框架动态解析落空（触发落 160k 兜底、保留落条数模式）⇒ 尾巴少量消息即可承载十几万 token（子任务回执、大工具结果），压缩后 token 几乎不降，阈值持续满足形成反复压缩。

修法（已落地）：

- 框架：`buildDeclaredFactory` 补齐 `compactionConfig` / `disableCompaction` / `toolResultEvictionConfig` 传播，与 general-purpose 工厂对齐；
- 平台：`CompactionConfig` 增加 `triggerTokens=96_000`（显式触发，不依赖模型上报窗口，同时把单次摘要输入规模限制在有界区间）与 `keepTokens=24_000`（按 token 从尾向前定截断点，保证压缩后上下文有界）；条数阈值保留作兜底。

### 3.9 用户「停止」意图对自发 run 链路不生效——中断后被多路看护反复复活

缺陷机制：interrupt 只终止当前 run。此后一切自发 run 唤醒源只认「会话空闲 + 有待办」，不感知用户已表达停止意图，会把「刚被停掉」误判成「有待办该继续」，循环拉起：

1. **框架子任务完成回调**：被中断 run 的子智能体完成 → 回调 push inbox hint + enqueue wakeup（事件驱动，清数据跑不赢推送）；
2. **TaskDeliveryWatchdog**（60s 扫描）：台账里「终态未投递」任务 → push hint + wakeup + markDelivered；
3. **InboxWatchdogWakeupService**（30s 扫描）：inbox 文件积压 + 会话空闲 → 补醒；
4. **SessionProgressService 停滞看护**：`next_action=CONTINUE` + idle>8min + inbox 空 → 注入自检消息强行续跑。这一路无数据可清——只要尾语归类为 CONTINUE 就会醒。

伴生缺陷（未修，另立）：自发 run 派生同步等待子任务时，interrupt 触发的框架 `InterruptControl.trigger(USER)` 取消不生效（`run still active`），只能等 run 自然收尾——补强杀路径（kill 子 run 租约 + 逐个 cancel）后续再做。

**已实现：会话级「用户停止」抑制标记（V60）**

- 存储：`agent_session_progress.stop_requested`（`V60__session_stop_requested.sql`）。进度 upsert 对该列「冲突时保留旧值」，运行期进度刷新不会抹掉标记；唯一写入口是显式方法。
- 置位：interrupt 端点受理后 `markStopRequested(true)`（无论当时是否有在跑 run——用户表达停止意图本身即置位条件）。
- 清除：用户主动发起新 run（`PlatformAguiRuntimeContextResolver.resolve`）置回 false。自发 run 不清除。
- 检查点（两处覆盖全部唤醒源）：
  - `AguiWakeupTarget.runWakeup` 入口——框架 wakeup、收件箱补醒、任务补投递、启动恢复四路都经 `enqueueWakeup` 汇聚于此；抑制时直接返回空，inbox hint 原样保留（用户下次「继续」仍可见积压）；
  - `SessionProgressService.shouldWake`——停滞看护自检注入被抑制。

验证：中断一个在跑的编排会话 → 观察至少 10 分钟（覆盖 Progress watchdog 8min 阈值 + 两轮 60s 扫描）无任何 wakeup 日志、run-status 恒为 false；再给该会话发一条新消息 → 标记清除、后续自发唤醒恢复。

验证：`mvn -o compile` + javap 验字节码 + 起服务后用现有会话冒烟（后台派发后事件库应能查到）。分批 commit。

### 3.11 客户端断连即中断 run——脚本/代理调 `/agui/run` 必须全程持流

- 机制（框架已内建开关，平台未配置走默认）：`AguiProperties`（prefix `agentscope.agui`）的 `interruptOnDisconnect` **默认 `true`**；MVC 与 WebFlux 两条 SSE 路径在 `onTimeout` / `onError` 回调里都按该开关执行 `interruptAndCancel`。平台 `application.yml` 只配了 `sse-timeout` / `run-timeout` 等，未覆盖此项 ⇒ 断连即掐 run。日志特征 `SSE connection error for run ...: interrupting agent`。
- 后果：任何调用方（无人值守脚本、curl 探针、反向代理超时）只要不把 SSE 读到 `RUN_FINISHED`——提前关闭、读头几 KB 即关、客户端超时——都会中断在跑的 run，且无任何面向用户的告警。
- 修法（零代码）：`application.yml` 增加 `agentscope.agui.interrupt-on-disconnect: false`，重启生效。断连后 run 继续跑完、事件照常落库；用户主动停止走 interrupt 端点（3.9 的停止抑制链已覆盖中断后的复活问题），语义不冲突。
- 验证：对测试会话发起 run 后客户端主动断开，观察 run 继续产出、agui_events 持续追加至 RUN_FINISHED；再验证 interrupt 端点仍能正常停止。

### 3.13 完成契约 + 决策事实化——「是否真完成」从文本猜测换成产出核验

- 判定分层：**停滞检测是物理事实**（无新消息 + 无租约 + 无闸门 + inbox 空 + 未喊停，零误报，永远可靠）；有语义误差的只是**处置层**（静止的会话该不该拉起）。3.13 把处置层的判定基准也事实化：
  1. **完成契约**：智能体在会话工作区落件 `session-complete.json`（deliverables 逐项 path/sha256/minBytes），平台逐项核验（存在/字节下限/指纹一致）⇒ VERIFIED = 确定性终态。落件后被修改未重新声明 ⇒ 指纹失配 ⇒ 完成状态自动失效。立过计划（plan/ 目录）的会话契约 MISSING/INVALID ⇒ 无论文本怎么说都不算完成。
  2. **纯文本收尾登记（V61 `last_text_ending_at`）**：run 级宣告式收尾检测器改为只观察登记、不做决策（run 结束瞬间拿不到 waitingHuman/stop/契约事实，靠 pattern 猜措辞已被证伪）；停滞看护读到「登记时间过宽限期（默认 3 分钟）+ 其后无新消息 + 契约未核验 + 非等人工」⇒ 提前补醒，不等满停滞阈值，提示词带核验失败明细（两个出口——落标记 / 继续干活——都是可验证动作）。
  3. **pattern 全量移除**：`DeclarativeEndingProperties.patterns/matchesAny`、检测器 pattern 门、DONE 文本兜底（3.12 原方案）全部删除。残留语义问题仅剩「纯文本提问式收尾」，由三层兜底：等人工走 HITL 表单约定 + 自检提示守卫句 + 补醒预算封顶（误唤醒代价一次空转轮 ≪ 漏唤醒的小时级停滞）。
- 无工作痕迹的纯问答会话不适用契约，回落原文本 DONE 语义。
- 落地：V61 迁移 + `SessionCompletionContractService` + 看护三态接入 + 检测器改观察登记 + AGENTS.md「完成契约」协议节；契约对全部智能体生效（约定写进 AGENTS.md 的智能体即刻受益，其余智能体首次被契约补醒时落件即可）。

### 3.14 事件级工具进度心跳——「合法长工具执行」不再被静默看护误杀

- 机制缺口：agent 事件只在轮与轮之间产生，单个工具执行期是事件黑盒——一个 56 分钟的前台安装命令与一条挂死的命令在事件流上完全不可区分，RunSilenceDetector 按 60 分钟自动恢复时会误杀前者（且此时 task 尚未产出，需重派整路）。
- 方案：框架新增 `ToolProgressHeartbeatMiddleware`（agentscope-harness），acting 阶段每 30 秒发一条 `tool_progress` 自定义事件（在途工具 id/名称 + 已耗秒数）。事件走既有管道：AG-UI 映射为 CUSTOM 事件、进 transcript 与事件库，`SessionActivityMiddleware` 逐事件 touch 事件时钟 ⇒ 合法长工具执行期间静默时钟持续被喂饱，不告警、不误恢复；前端暂忽略 CUSTOM 事件（进度可见性以事件库/日志为准，UI 呈现后续项）。
- 停滞检测安全性：心跳是「经过时间」驱动，若无限发射会把真挂死的工具永久掩护 ⇒ 发射窗口封顶（`toolHeartbeatWindow`，平台取 30 分钟，与工具执行兜底超时同量级）。超窗后心跳停止、时钟重新归于静默，真挂死仍被看护按原阈值识别接管。
- 装配：`AgentAssemblyService` builder 链 `.toolHeartbeat(30s)/.toolHeartbeatWindow(30min)`，随 AsyncToolMiddleware 同点注册（messageBus 存在时）。框架 install 带 `-Drevision=2.0.3-tipdm`，**重启后端生效**。
