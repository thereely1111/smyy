## 输入

| 参数          | 路径                                                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 目录结构.json | `artifacts/{教材名称}/章节目录/目录结构.json`                                                                                    |
| 案例清单.json | `artifacts/{教材名称}/章节目录/案例清单.json`                                                                                    |
| 知识概要.md   | `artifacts/{教材名称}/章节目录/知识概要.md`（只读取本章 `项目实现` 部分）                                                      |

> **路径（本 Skill 的输入/产出）**：**输入**文件路径由父编排在 task 中注入，是**绝对路径**（运行态根 + 产出方会话目录 + 相对路径），**原样使用**，**禁止**用相对路径去猜；**产出**一律用**相对路径**写在自己的会话空间（会话之间不共享目录），并在 `【TASK_RESULT】artifacts` 里逐文件登记（`<自身会话目录>/<相对路径>`）。完整规则见 `jc-0-路径工具`。

## 工作流程

### Step 1：读取与判断

1. 读取目录结构.json（含 `思政_required`）、案例清单.json、知识准备内容、知识概要.md（本章「项目实现」部分）
2. 读取案例原文和资料来源（`_索引.json` → `资料全文/`）
3. 读取数据文件
4. 按需加载模板：始终加载 `references/全局写作原则.md` + `用语与格式规范.md`；涉及思政（`思政_required=true` 时加载 `思政融入规范.md`）/代码/表格/公式时按需加载对应规范
5. 从案例清单.json 定位该 H2 对应的示例或案例，并读取该条目的 `usable`、`modification` 与 `stages[].source` 字段（`usable` 决定案例处置方式，`modification` 记录修改/补充建议，`stages[].source` 决定逐阶段内容来源：`KB`=案例原文已有、`AI`=案例原文没有需补充）

**提示词驱动内容**：当该 H2 的实现涉及"借助AI""提示词""AI生成"等协作流程时，额外加载 `references/提示词驱动型知识结构.md`，遵循其中的「描述 → 提示词 → 描述 → 结果」四段式展示规范。结果来源两路处理：来源已有结果 → 引用；来源无结果 → 由内置 AI 真实运行提示词产出结果。

**项目实施提示词硬约束（强制执行）**：

1. **必须参考案例文档**：项目实施的提示词必须基于 `案例资料/{案例名}/` 中的真实案例代码/原型编写，与知识准备的提示词差异化（知识准备重"讲方法"，项目实施重"产出真实结果"），禁止照抄知识准备提示词、禁止仅改编号复用；
2. **必须输出运行结果**：每个项目实施的提示词后，必须紧跟【运行结果】段，引用案例配套代码中的真实文件（标注"以下为AI根据提示词生成的代码（{文件路径}）："）或内置 AI 真实运行输出，禁止省略结果段、禁止用"AI 生成原型后……"的笼统描述替代；
3. 结果呈现遵循 `references/提示词驱动型知识结构.md` 第三节四段式与第四节代码块标注规则。

### Step 2：编写导入

#### 项目任务式 →【任务描述】

任务描述必须具有实际意义，主要是一段话，分为 4 个部分：

| 部分        | 内容                                                                 |
| ----------- | -------------------------------------------------------------------- |
| ① 理论背景 | 一句话（概念、作用等）引入，解释任务的理论背景，即知识点与任务的关系 |
| ② 实际背景 | 这个具体任务的实际背景                                               |
| ③ 操作原因 | 为什么要做这个任务（原因要符合实际，不为了操作而操作）               |
| ④ 任务目标 | 这个任务具体目标是什么                                               |

纯理论型任务：任务描述主要写该二级标题的意义。

#### 项目式 →【项目描述】

项目描述由项目背景、项目目标、项目分析组成，**也可能只有项目背景**。按结构分两种模式：

| 模式       | 条件                  | 结构                           |
| ---------- | --------------------- | ------------------------------ |
| 仅项目背景 | 无项目目标、项目分析  | 项目背景（目标融入背景段落）   |
| 完整三部分 | 有项目目标 + 项目分析 | 项目背景 + 项目目标 + 项目分析 |

**（1）项目背景**：具有实际意义，贴近读者生活。按章节类型分三种写法：

| 案例组织模式                       | 写法                                                                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 单章案例式、全书贯穿式             | 先描述行业/技术背景、发展现状、目标与挑战 → 引入案例数据、讲解数据字段 → 介绍案例目标 → 得出应使用的技术 |
| 理论/工具类                        | 写该技术的发展历程、发展现状、热点事件，或应用领域                                                          |
| 先导实战式、综合是案例式（案例章） | 描述相关行业和技术的背景及发展现状，不描述案例具体情况                                                      |

同时需满足：简略介绍本章主要内容（1~2 行，不超过 3 行）；体现本章与本书的关系。

**（2）项目目标**：基于项目背景中的问题得出的主要目标，是大目标（非拆细目标），可分点但一般不超过 3 点。

**（3）项目分析**：基于项目目标拆解出的具体步骤，即实现项目目标的步骤。

> 仅项目背景时（无项目目标、项目分析），需在背景段落中补充项目目标。

**思政判断**：若 `思政_required = true`，项目背景融入思政元素；若 `false`，不融入。

### Step 3：编写实现

- **项目任务式 →【任务实现】**：基于知识准备内容，完成该 H2 的任务。标题为动宾结构
- **项目式 →【项目实施】**：基于知识准备内容，实施项目。标题为动宾结构

**与知识准备的衔接**：实现部分不重复讲概念，直接演示操作。

**案例处置（按案例清单 `usable` × `stages[].source` 字段）**：实现前先判断该 H2 对应案例的 `usable`，并逐阶段读取 `stages[].source`，决定如何基于案例原文编写：

| `usable` | 处理方式                                                                                                              |
| ---------- | --------------------------------------------------------------------------------------------------------------------- |
| `复用`   | 直接引用案例原文，不改动案例选题与主体内容                                                                            |
| `修改`   | **按 `modification` 字段的修改建议，对案例原文进行裁剪/调整**（如裁剪超纲知识点、替换数据、调整步骤）后再写入 |
| `补充`   | 保留案例原文，**按 `modification` 字段补充缺失知识点**对应内容                                                |
| `AI推断` | 无来源案例，按知识准备内容自行实现                                                                                    |

**案例原文优先（强制，按 `stages[].source` 逐阶段执行）**：在 `usable` 档位之上，进一步按 `stages[].source` 区分内容来源，凡案例原文中已有且满足本章 H2 要求的代码/提示词/数据/运行结果，**必须直接复用，不得另写一套、不得弃之不用**：

| `stages[].source` | 处理方式                                                                                       |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| `KB`              | 案例原文已提供该阶段内容 → **必须直接复用案例原文的代码/提示词/数据/结果**，不得另写、不得弃用 |
| `AI`              | 案例原文没有该阶段内容 → **允许按 `modification` 补充**，且须基于知识准备知识点编写           |

> `modification` 是案例"四路处置"结论的落点：`复用` 时为 null，`修改`/`补充` 时为具体修改/补充建议。编写实现时**必须执行 modification 建议**，不可忽略或另起炉灶。`stages[].source="KB"` 的阶段若弃用案例原文另写，属违规。

### Step 4：生成图片清单

实现编写完成后，对正文中每个需要配图的位置，遵循 `references/配图规范.md` 的「两步判定」：

1. 先查 KB 图片索引（资料来源为 KB 且原文有图 → 命中直接引用，不纳入清单）
2. 未命中再按配图类型分型（代码生图 / AI生图 / 待补齐）

@图片清单写入项目实现 Markdown 末尾，供 jc-3-视觉素材 批量生成。

### Step 5：代码验证

涉及代码编写时，按 `jc-0-代码验证` 规范执行：本地化 → install.py → execute_code.py → 失败修复（≤3轮）。

## 核心约束

1. **不重复知识准备**：实现部分直接操作演示
2. **导入对应实现**：导入中描述的问题，实现中必须完成
3. **体例强制**：按体例类型输出对应组件，不可混用
4. **动宾标题**：任务实现/项目实施下的标题为动宾结构
5. **有数据用数据**：案例清单中该 H2 有数据则使用，无数据则使用常量或内置示例
6. **必须执行 modification**：案例 `usable="修改"/"补充"` 时，必须按 `modification` 字段的修改/补充建议落实，不可忽略、不可另起炉灶；`usable="复用"` 时直接引用原文不改动
7. **案例原文优先**：`stages[].source="KB"` 的阶段，案例原文已有且满足本章 H2 要求的代码/提示词/数据/运行结果**必须直接复用**，弃用另写即违规；`source="AI"` 的阶段才允许按 `modification` 补充

## 修改模式

收到 `[修改指令]` 时：仅修改指出的问题点，逐条对照修正。
