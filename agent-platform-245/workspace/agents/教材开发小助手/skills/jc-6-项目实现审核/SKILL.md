## 输入上下文

- **项目实现组件**：`组件/项目实现.md`（任务描述+任务实现 / 项目描述+项目实施）
- **体例类型**：`目录结构.json` 顶层字段「体例类型」（项目式 / 项目任务式）
- **知识准备内容**：`知识准备.md`（供对比「实现与知识准备衔接」）
- **章节目录**：当前章节标题树
- **案例清单**：`章节目录/案例清单.json`（核对 `stages[].source` 的案例原文复用）
- **资料来源**：`资料全文/第X章_资料来源.md`（技术审核核实出处）

> **路径（本 Skill 的输入/产出）**：**输入**文件路径由父编排在 task 中注入，是**绝对路径**（运行态根 + 产出方会话目录 + 相对路径），**原样使用**，**禁止**用相对路径去猜；**产出**一律用**相对路径**写在自己的会话空间（会话之间不共享目录），并在 `【TASK_RESULT】artifacts` 里逐文件登记（`<自身会话目录>/<相对路径>`）。完整规则见 `jc-0-路径工具`。

## 执行方式

**自动化脚本 + AI 语义并列审核。脚本与AI独立运行，合并判定：任一方不通过即为整体不通过。**

### 第一步：运行自动化规则检查
```bash
python scripts/audit_project_impl.py <待审核内容.md>
```

**脚本输出**（stdout，结构化文本）：

| 检查项 | 说明 |
|--------|------|
| 导入结构 | 任务描述4部分 / 项目描述（背景+目标+分析）段落存在性 |
| 项目背景结构 | 项目背景（背景→数据字段→目标→技术→内容预览→全书关系）结构线索 |
| 动宾标题 | 任务实现/项目实施下三级标题数量（动宾语义由 AI 判断） |
| 代码-结果配对 | 每个 代码X-N 是否有对应的 运行代码X-N 结果 |
| 题注引用 | 图/表/代码是否有前置引用句式 |
| 编号连续性 | 代码编号连续无缺号/重号 |
| 敏感词/人称/时间词 | 敏感词、人称代词、模糊时间词粗检 |

> 代码复跑验证由生成端 `jc-3-项目实现` Step 5（`jc-0-代码验证`）完成；本审核脚本核对代码-结果配对与编号，不复跑。

脚本独立输出审核结论（通过/不通过 + 检查项明细）。不产生任何持久化文件。

### 第二步：AI 语义审核
读取被审核文件实际内容，独立输出审核结论。

**1. 导入结构（任务描述 / 项目描述）**

- 任务描述（项目任务式）：4 部分齐全——理论背景（知识点与任务关系）→ 实际背景 → 操作原因 → 任务目标；纯理论型写该标题的意义
- 项目描述（项目式）：项目背景（有实际意义、贴近读者、含案例数据字段说明）+ 项目目标（大目标，≤3点）+ 项目分析（步骤拆解）；仅项目背景时目标须融入背景
- 项目背景体现本章与本书关系
- 任务/项目背景描述客观、全面

**2. 实现与知识准备衔接**

- 实现部分不重复讲概念，直接演示操作
- 导入中描述的问题，实现中必须完成（对应关系检查）
- 实现用到的知识点是否在知识准备中有介绍

**3. 技术审核（一审技术审核主战场之一）**

- **代码结果核对**：核对每个代码是否有对应运行结果、结果与正文描述是否一致（代码复跑由生成端 `jc-0-代码验证` 完成，本步核对结果段落的存在性与一致性）
- 技术名词使用是否恰当、是否有权威解释
- 代码输入输出、变量名、注释、结构完整性、可读性
- 输出结果与正文内容联系，是否为内容提供依据

**4. 来源核对与捏造检查（强制，严禁胡编乱造）**

> 打开 `资料全文/第X章_资料来源.md`，逐项核对实现部分的案例数据、代码、技术细节是否来自来源原文。

- **逐项溯源**：案例背景数据、数据集字段、代码逻辑、API 调用、输出结果等，必须能在资料来源原文中找到对应支撑
- **查捏造**：以下内容来源原文不存在即判定捏造，**不得以"合理推断"为由放过**：
  - 案例中出现的具体数据、字段名、字段值
  - 来源未提供的代码片段、API 名称、参数
  - 来源未提供的运行结果、输出样例、图表数据
  - 来源未提供的性能对比、结论性表述
- **边界处理**：来源未覆盖的细节，实现部分**不得自行补造**；确需补充时须退回 `jc-3-项目实现` 先补来源再编写
- **输出**：`[来源核对通过 N/N]` 或 `[捏造风险 @位置: "具体表述" → 来源无此内容]`

**4-1. 案例原文复用核对（强制）**

> 打开 `案例清单.json`，定位本章条目的 `stages[].source`，逐阶段核对实现部分的代码/提示词/数据/运行结果是否复用案例原文。

- **`source="KB"` 的阶段**：案例原文已有且满足本章要求的内容，实现部分**必须复用案例原文**；若实现内容与案例原文明显不符（另写一套、弃用原文），且非 `modification` 字段所述改动 → 判为「弃用案例原文另写」，不通过
- **`source="AI"` 的阶段**：案例原文没有该内容，允许按 `modification` 补充，核对补充内容是否落实 `modification` 建议、是否基于知识准备知识点
- **输出**：`[案例原文复用核对通过]` 或 `[弃用案例原文 @位置: "stage名称" source=KB → 实现内容与案例原文不符]`

**5. 题注引用与编号**

- 图/表/代码是否有前置引用句式（如图X-N所示/如代码X-N所示）
- 代码编号是否连续、按二级标题重置
- 代码-结果是否配对

**5-1. 提示词运行结果完整性**

- 凡含"提示词""借助AI""AI生成"等提示词驱动型内容的 H3/H4，必须满足四段式「描述→提示词→描述→结果」
- 「结果」段为必选：提示词后必须紧跟运行结果（代码块 `代码X-N` + 来源标注，或引用块 `结果X-N`），并标注来源（"以下为AI根据提示词生成" / "以下为内置 AI 实际运行输出"）
- 禁止：提示词后无结果段，或仅用"AI 生成原型后……"的笼统描述替代结果
- 判定：违反上述任一 → 该组件审核不通过，退回 `jc-3-项目实现` 补充结果段

**6. 思政融入**

- 若 `思政_required=true`，项目背景是否自然融入思政；否则不融入

### 第三步：合并判定

脚本与AI各自独立给出通过/不通过结论。**任一方不通过 → 整体不通过**。汇总双方所有不通过点，统一输出。

## 输出格式

```
[审核结果] 通过 / 不通过

## 脚本审核：[通过/不通过]
（脚本输出的检查项明细：通过项 + 不通过项）

## AI审核：[通过/不通过]
通过项：（列出所有AI通过的检查项）
不通过项：（每项注明具体位置、问题描述、修改建议）

[综合评定]
脚本与AI合并判定：双方均通过 → 整体通过；任一方不通过 → 整体不通过。
汇总双方所有不通过点与修改建议。
```

## 修改模式

收到 `[修改指令]` 时：仅对反馈涉及的问题点重新审核，其余已通过项保持结论不变。
